# 第 2 阶段：从解析函数到可使用的求职助手 MVP

## 产品闭环

用户在 Streamlit 页面上传简历、粘贴 JD，单 Agent 工作流依次执行解析、要求识别、证据定位、评分和 SQLite 记录。FastAPI 暴露同一套能力，方便后续接前端或部署。

```text
Streamlit / FastAPI
        ↓
JobAnalysisWorkflow
        ↓
简历解析 → JD 要求识别 → 证据匹配 → 事实约束 → SQLite
```

规则基线不是最终产品卖点，而是可测试的底座。之后接入大模型时，模型负责同义表达、职责理解和文案生成；明确技能、年限、学历和原文证据仍由确定性代码校验，避免模型编造经历。

## 为什么同时使用 FastAPI 和 Streamlit

- Streamlit 用较少代码交付可操作页面，适合快速验证工作流。
- FastAPI 把核心能力变成稳定接口，使页面、自动化脚本或未来前端都能复用。
- 两者都调用同一个工作流服务，避免出现两套业务逻辑。

## 面试表达

“我先交付了一个端到端 MVP，而不是孤立的提示词 Demo。它支持浏览器上传三种简历格式，输出带原文证据的岗位匹配报告，通过 FastAPI 暴露接口，并用 SQLite 留存任务。隐私上不持久化整份简历，命中证据会遮蔽手机号、邮箱和微信号，上传文件只进入临时目录；架构上把规则基线封装为可替换模块，为后续 LLM 增强和离线评估保留了清晰边界。”

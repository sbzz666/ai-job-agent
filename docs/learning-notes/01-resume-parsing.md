# 第 1 阶段：先让简历变成可靠文本

## 为什么不先调用大模型

模型只能分析它收到的文本。如果 PDF 没抽出文字、Word 表格被遗漏或编码乱码，后面的匹配分数和建议都会失真。因此第一阶段先把文档解析做成一个独立、可测试的本地工具。

## 作用与数据流

```text
本地文件 → 校验路径/格式 → 格式解析器 → 清洗空白 → ParsedResume
```

`ParsedResume` 是统一数据契约。后续职位匹配模块只依赖这个对象，不关心原文件是 TXT、Word 还是 PDF。

## 三种格式

- TXT：依次尝试 UTF-8 BOM、UTF-8、GB18030，兼顾常见中文文件。
- DOCX：用 `python-docx` 提取普通段落和表格单元格；若正文位于简历模板常用的文本框/绘图中，则只读解压 OOXML 并提取底层文字节点作为回退。
- PDF：用 `PyMuPDF` 按页提取文字，并保留页数供后续证据引用使用。

扫描版 PDF 本质上是图片，当前会明确拒绝空文本；OCR 将作为后续扩展，而不是静默地产生错误结果。

## 为什么用 Pydantic

Pydantic 把解析结果约束成稳定结构，并在运行时校验文本非空、计数为正。未来 FastAPI 可直接复用同一个模型生成接口校验和文档。

## 面试中如何表达

“我没有一开始把文件内容直接交给 LLM，而是先实现格式无关的摄取层。它支持 TXT、DOCX、PDF，覆盖 Word 表格、中文编码、空文件、损坏文件和扫描 PDF 等边界情况，并通过 Pydantic 输出统一结构。这样后续匹配、证据定位和事实校验都可独立测试，也降低了隐私泄露风险。”

## 隐私规则

- 真实简历保留在仓库外，测试使用虚构数据动态生成。
- CLI 默认只显示文件名和统计信息，不打印正文。
- API Key 只从环境变量读取；`.env` 已被 Git 忽略。
- 任何将真实文本交给外部模型的功能，都应先明确提示数据边界。

## 本阶段验收

运行 `pytest`，TXT、DOCX、PDF 的正常路径以及不支持格式、空文件异常均应通过。
